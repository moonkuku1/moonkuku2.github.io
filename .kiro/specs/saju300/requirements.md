# 사주300 요구사항 (requirements.md)

- 기준 문서: `docs/business-plan.md` (이 문서와 충돌하면 기준 문서가 우선)
- 질문 데이터: `data/questions.json` (240문항, 8개 카테고리, 현재 모두 `status: "draft"`)
- 저장소: GitHub `saju300-new` → 새 Vercel 프로젝트. 기존 사이트(saju300.vercel.app, `moonkuku1.github.io`)는 건드리지 않는다.
- 문장 형식: "WHEN(언제) … THEN(그러면) 시스템은 … 해야 한다" 형식으로 적는다. 각 항목이 나중에 테스트로 확인할 기준이 된다.

---

## 용어

| 용어 | 뜻 |
|---|---|
| 명식 | 사주 8글자(연·월·일·시주)와 계산 결과 전체 |
| 사주 프로필 | 명식으로 한 번 만들어 저장하는 키워드 3개·인생 테마·강점·조심할 점 (P1) |
| 레시피 | 질문마다 "어떤 신호를 보고, 어떻게 판정하는지" 적은 데이터 (`data/recipes.json`) |
| 신호 | 사주에서 계산되는 판정 재료 하나 (예: 세운에 배우자성). 신호 하나 = 순수 함수 하나 |
| 판정 | 질문의 결론. 코드가 정한다 (예: "2027년 5월과 9월") |
| 확신도 | 강·중·약. 코드가 정한다 |
| 근거 칩 | 판정 옆에 붙는 [세운 정관] 같은 작은 라벨. 계산값에서만 나온다 |
| 테스트 결제 모드 | 실제 돈이 나가지 않고 결제 흐름만 끝까지 진행되는 개발용 모드 |

## 1. 만세력 계산 (lib/saju)

**목적**: 모든 답의 바탕. 여기가 틀리면 이후 전부 틀리므로 가장 먼저, 가장 꼼꼼히 검증한다.

1.1 WHEN 양력 생년월일·시각·성별을 받으면 THEN 시스템은 연·월·일·시주 8글자를 계산해야 한다.
1.2 WHEN 음력 생년월일(윤달 여부 포함)을 받으면 THEN 시스템은 양력으로 바꾼 뒤 계산해야 한다.
1.3 연주는 입춘 시각 기준으로, 월주는 각 절기의 절입 시각 기준으로 바뀌어야 한다. (양력 1일 기준 금지)
1.4 자시(23:00~01:00)는 기본 설정으로 처리하고, 야자시 옵션을 켜면 23시대를 당일 일주로 계산해야 한다.
1.4-1 야자시 옵션이 꺼진 기본 설정에서는 23:00~23:59도 자시로 보고 일주는 다음 날 것을 쓴다(시주는 다음 날 일간의 자시). 옵션을 켜면 일주는 당일, 시주는 당일 일간의 자시를 쓴다. 00:00~00:59는 어느 쪽이든 당일이다. (구현: `lib/saju/day-hour.ts`)
1.5 한국 서머타임 시행 기간에 태어난 경우 THEN 시스템은 1시간을 보정해야 한다.
1.5-1 (확인 필요) 1954-03-21~1961-08-09는 한국 표준시가 지금보다 30분 늦은 동경 127.5° 기준이었고, 서울의 실제 경도 시차(약 -32분)를 출생 시각에 반영할지는 만세력마다 다르다. 사장님이 방침을 정하기 전까지는 한국천문연구원 기준 날짜·시각을 그대로 쓰고, 경도 보정은 옵션으로만 둔다.
1.6 WHEN 출생 시간이 "모름"이면 THEN 시스템은 시주를 빼고 계산하고, 결과에 "시간 모름"을 표시하며, 확신도를 한 단계 낮춰야 한다.
1.7 시스템은 오행·십성 분포, 신강·신약, 격국, 용신, 합·충·형·파·해·원진, 신살(도화·홍염·화개·역마·천을귀인·문창귀인·백호·괴강·귀문관·삼재, 12신살), 대운(시작 나이·순서)·세운·월운을 계산해야 한다.
1.8 계산 결과는 JSON 하나로 묶어 저장하고, 같은 입력이면 항상 같은 JSON이 나와야 한다.
1.9 테스트: 기준 생년월일 20개 이상 + 입춘일·절입일·자시·서머타임 경계 케이스. 기댓값은 한국천문연구원 자료로 확인한다. **이 테스트가 모두 통과해야 다음 단계로 넘어간다.**

## 2. 신호·판정 엔진 (lib/signals, lib/verdict)

2.1 시스템은 40~60개의 공통 신호를 각각 독립된 순수 함수로 제공하고, 신호마다 테스트가 있어야 한다.
2.2 레시피는 `data/recipes.json`에 질문 ID별로 `verdictType`, `timingScope`, `signals`(key·label·weight·dir), `verdictRule`, `safety`를 가져야 한다.
2.3 처음에는 카테고리별 인기 질문 10개(총 60개 이하)만 정교한 레시피를 쓰고, 나머지 질문은 카테고리 공통 레시피를 써야 한다.
2.4 WHEN 명식과 질문 ID를 받으면 THEN 시스템은 판정·확신도·시기·지지 신호·반대 신호를 계산해야 한다.
2.5 확신도 = 지지 점수 합 − 반대 점수 합. 5 이상 강, 2~4 중, 1 이하 약. 출생 시간이 없으면 한 단계 낮춘다.
2.6 시기는 계산된 대운·세운·월운 안에서만 골라야 한다.
2.7 궁합(2인) 점수·등급, 신년운세 월별 점수도 코드가 계산해야 한다.
2.8 같은 명식 + 같은 질문 + 같은 기준 연월이면 판정이 항상 같아야 한다 (테스트로 확인).

## 3. AI 문장 생성 (lib/llm)

3.1 프롬프트 P1~P6은 기준 문서 8장의 문구를 그대로 `lib/llm/prompts/` 파일로 옮겨 써야 한다.
3.2 AI 호출은 서버에서만 하고, API 키는 `.env.local`에만 둔다. 브라우저 코드에 키가 들어가면 안 된다.
3.3 temperature는 0~0.3으로 고정한다.
3.4 P1(사주 프로필)은 명식당 한 번만 만들고 저장해 재사용한다.
3.5 P2(답변)는 판정·확신도·시기를 바꾸지 않고 문장만 쓴다. 출력 JSON은 headline·evidence·story·counter·action·avoid·confidenceNote 형식이다.
3.6 P5 코드 검수는 매번 한다: JSON 형식, 근거 칩이 지지 신호 안에 있는지, headline에 판정 값이 있는지, 글자 수, 금지어. 실패하면 1회 다시 만들고, 또 실패하면 운영자에게 알린다.
3.7 P5 AI 검수는 답변의 5%만 표본으로 한다.
3.8 캐시 키는 (명식 해시 + 질문 ID + 기준 연월)이다. WHEN 같은 키의 답이 있으면 THEN AI를 부르지 않고 저장된 답을 보여줘야 한다.
3.9 WHEN AI 키가 아직 없으면 THEN 시스템은 "샘플 문장 모드"로 동작해 화면 흐름을 끝까지 확인할 수 있어야 한다. (판정·근거 칩은 실제 계산값 사용)
3.9-1 AI 회사는 코드 한 곳(설정)만 바꾸면 교체할 수 있어야 한다. 모델은 질문당 AI 비용 30원 이하 목표에 맞춰 고르고, 실제 한국어 답변 품질을 비교한 뒤 확정한다 (설계 문서의 비교표 참고).
3.10 모든 결과 하단에 "참고용 해석이며 의료·법률·투자 판단을 대신하지 않습니다"를 표시한다.
3.11 건강·임신·투자·법률 관련 질문(questions.json의 note에 단정 금지가 적힌 질문 포함)은 단정하지 않고 전문가 상담을 권해야 한다.

## 4. 화면

공통 디자인 (기준: `docs/design-guide.md`, `.kiro/steering/design.md`. 색·글꼴·크기 값은 이 문서를 따른다)
4.1 WHEN 어떤 화면이든 그릴 때 THEN 시스템은 남색 달밤(night #04101E) 바탕, 한지(#EFE4CC) 판정·답변 카드, 금색(#D9B46A) 포인트의 민화 톤을 써야 한다. 주황(#E8732A)은 결제·질문하기 버튼에만 쓴다.
4.1-1 색·글꼴·모서리 값은 Tailwind 설정(`theme.extend`)에 디자인 토큰으로 한 번만 정의하고, 화면 코드에서 색 값을 직접 쓰지 않는다. 오행 색은 명식표에만 쓴다.
4.1-2 글꼴은 Song Myung(대사·포스터 제목), Noto Serif KR(제목·판정·한자), Noto Sans KR(본문·버튼)을 쓰고, 한글은 `word-break: keep-all`, 가격 숫자는 `tabular-nums`로 한다.
4.2 글자와 배경의 명도 대비는 본문 4.5:1 이상, 큰 제목 3:1 이상(WCAG AA)이어야 한다. 사진 위 글자에는 어두운 막을 깐다.
4.3 모든 화면은 휴대폰 너비 390px 기준으로 맞추고 최대 480px 가운데 정렬로 둔다(PC에서도 같은 화면을 가운데에 놓는다). 눌러서 반응하는 모든 요소는 44×44px 이상이고, 키보드로 모두 누를 수 있어야 한다.
4.4 그림은 `public/images/saju300-images/`의 파일만 쓰고, 파일별 쓰임은 design-guide.md의 ‘그림 파일’ 절을 따른다. 설명이 필요한 그림은 `alt`를 쓰고 꾸밈 그림은 `alt=""`로 한다. 그림 파일이 없는 항목은 대체 그림을 보여준다.
4.4-1 풀이꾼은 질문 카테고리로 정한다: 연애·결혼·궁합은 삼백 아씨, 일·재물·시험·가족은 삼백 도령, 판정 도장·오늘 한 마디·올해·나는 해치 삼백이. 이 짝은 코드 한 곳(카테고리 설정 데이터)에서만 관리한다.
4.4-2 해치 포즈는 판정에 따라 바꾼다: 좋은 판정은 haechi-joy, 조심 판정은 haechi-think, 판정 도장은 haechi-stamp.
4.4-3 움직임은 잔잔한 것만 쓴다: 판정 도장 찍히기, 배너·풀이꾼 그림의 느린 확대·이동, 배너 달빛, 해치 오르내림, PC 포스터 떠오름. `transform`·`opacity`만 쓰고, 화면 밖에 있으면 멈추며, `prefers-reduced-motion`이면 모두 끈다. (2026-11-14 사장님 결정으로 ‘도장 하나만’ 규칙을 바꿈)
4.4-4 한지 카드는 안쪽에 금선 한 줄, 카드 테두리는 1px 옅은 금색 또는 한지색으로 한다. 두꺼운 테두리와 비스듬한 그림자는 쓰지 않는다.

화면 목록
4.5 메인(모바일 홈): 위에서 아래로 다음 순서로 만든다.
  - 고정 헤더(해치 얼굴 로고, 장바구니 담은 개수 배지)와 탭(오늘·요즘 고민·주제별·풀이꾼·무료). 탭은 스크롤에 따라 지금 구역이 바로 바뀌고 누르면 그 구역으로 이동한다.
  - 풀이꾼 배너 3장(옆으로 넘기기, 3:4, 화면 너비 86%). 시즌 배너는 이 중 한 장의 대사·질문으로 반영한다.
  - 삼백이의 오늘 한 마디(무료, 년·월·일 선택, 한지 카드, ‘今日’ 도장, 300원 질문 링크)
  - 요즘 이런 고민 있어요(상황 카드 5장). 카드에는 상황 제목·한 줄 설명·"이 3개 한 번에 담기"만 보이고, 질문 3개는 접어 둔다. 질문 문장은 4.7 주제 페이지에서만 처음부터 보여서 겹치지 않는다.
  - 궁금한 주제 고르기(카테고리 포스터 8장, 휴대폰 2열·PC 4칸 × 2줄, 누르면 4.7 주제 페이지로 이동, 담은 개수 표시)
  - 사주300의 풀이꾼 장면 카드 3장, 300원 답변 예시 한지 카드, 무료 일주 카드 바로가기, 약속 3가지, 바닥글
  - 아래 고정 메뉴(홈·오늘 한 마디·내 풀이함·내 정보). 질문을 담으면 그 위에 “담은 질문 N개 · 합계 · 결제하고 바로 보기” 줄을 보인다.
  - 무료 사주 프로필 입력은 오늘 한 마디의 생일 입력과 같은 흐름으로 이어지며, 4.6의 프로필 카드로 연결한다.
4.6 무료 사주 프로필 카드: 명식표, 핵심 키워드 3개, 인생 테마, "내 사주가 궁금해할 질문 3개" 추천, 공유 이미지(인스타 스토리 크기). 가입 없이 볼 수 있고, 저장은 가입해야 한다.
4.7 카테고리별 질문 목록(`/c/[code]`): `data/questions.json`에서 읽어 그린다. 주제의 질문 전체(30문항)를 한 화면에 보여 주고(PC 2열), 질문을 장바구니에 담을 수 있다.
4.7-1 주제 페이지에는 담당 풀이꾼 소개(`data/guides.json`), "처음이라면 이 3개"(추천 질문, 판매 순위가 아님), 전체 선택/전체 해제(지금 보이는 질문 기준), "시기를 알려 주는 질문만" 필터(`includesTiming`), 아래 고정 요약(이 주제 개수·합계, 장바구니 전체)이 있어야 한다.
4.7-2 한 주제의 질문을 모두 담으면 묶음가(6.2)가 적용된다. 주제 페이지는 "30개 모두 담으면 묶음가 7,900원 (낱개 합계 9,000원 → 1,100원 덜 내요)"를 보여 주고, 장바구니는 낱개 합계와 묶음가 할인을 나눠서 보여 준다. 일부만 담으면 낱개 합계다. 가격은 `data/pricing.json`에서만 관리하며 사장님이 나중에 바꿀 수 있다(2026-11-14 확정, 이후 변경 가능).
4.7-3 풀이꾼의 역할은 `data/guides.json` 한 곳에서 관리한다: 삼백 아씨는 사람 사이의 마음과 인연, 삼백 도령은 결정해야 할 일과 현실 문제, 해치 삼백이는 큰 흐름과 판정 도장.
4.8 질문 소개 페이지(`/q/[id]`): 검색에 잡히는 공개 페이지. 개인 결과가 아니라 "사주로 이 질문을 보는 법"을 보여준다 (P6, 사람 검토 후 공개).
4.9 장바구니(`/cart`): 담은 질문, 합계, "함께 보면 좋은 질문" 3개, 결제 전 고지와 동의 체크.
4.9-1 장바구니는 주제별로 개수와 가격을 한 줄씩 요약하고(예: "연애 · 12개 · 3,600원"), 주제를 누르면 고른 질문이 보인다. "전체 문항 보기"를 누르면 그 주제의 전체 목록에서 고른 질문에 ✓가 표시되고, 여기서 바로 더 담거나 뺄 수 있다.
4.9-2 환불 제한 안내와 만 19세 이상 확인에 모두 체크하기 전에는 결제 버튼이 눌리지 않는다. 결제 연결 전에는 "실제 결제는 되지 않는다"는 안내만 보여 준다.
4.10 결과: 판정 → 근거 칩(누르면 쉬운 설명) → 확신도 → 해석 → 반대 신호 → 처방 1개 + 기한 → 피할 것. 하단에 이어볼 질문 추천과 도움됨/아님 버튼.
4.10-1 결과 화면의 모양은 design-guide.md의 ‘결과 화면’ 순서를 따르고, 값은 판정 엔진 결과를 그대로 쓴다(화면만 바꾸고 판정·확신도·시기는 바꾸지 않는다).
  - 헤더(← 내 풀이함) → 풀이꾼 장면(300px) 위에 풀이꾼 이름·카테고리·질문·생년월일 정보
  - 한지 판정 카드: 첫 줄 결론, 판정 도장(열릴 때 찍힘), 좋은/조심 흐름 표시, 확신도 3단계, 두 줄 요약
  - 언제가 좋을까: 12달 막대(좋은 달 금색+★, 조심할 달 붉은색)
  - 이렇게 본 근거: 명식 8글자(오행 색), 판정에 쓴 글자는 금색 테두리, 근거 3줄. 근거 칩은 이 영역에 둔다.
  - 솔직히 말하면(반대 신호 한 줄, 붉은 상자) → 이번 달 처방(해치 포함) → 이어서 물어보기(같은 풀이꾼의 다음 질문 3개 + 담기) → 하단 고정 버튼(판정 카드 공유 / 다른 질문 고르기)
4.10-2 결과 화면 끝에 “풀이는 참고용 해석이며 의료·법률·투자 판단을 대신하지 않습니다.”를 표시한다(3.10과 같음).
4.10-3 답변 본문(판정 문장·해석·반대 신호·처방)도 그 질문 담당 풀이꾼의 말투로 쓴다: 아씨는 다정한 "~해요", 도령은 점잖은 "~습니다/~지요", 해치 삼백이는 옛말투 반말. 이 항목은 기준 문서(`docs/business-plan.md`)의 "~해요"체 규칙보다 우선한다(2026-11-14 사장님 결정). 말투가 달라도 첫 줄 결론, 겁주는 말 금지, 건강·임신·투자·법률 단정 금지(3.11)는 똑같이 지킨다.
4.10-4 판정 엔진과 AI 문장 생성(3장)을 만들 때 P2 프롬프트에 풀이꾼 말투(`voice`)를 입력으로 넣고, P5 검수에 말투 확인을 더한다. 기준 문서의 P2 문구는 이 항목에 맞게 풀이꾼별 말투를 추가해 쓰되, 바꾸기 전에 사장님께 보여 드린다.
4.11 보관함: 산 답을 기한 없이 다시 보기, 내 사주 정보 수정, 알림 설정.
4.12 궁합 초대 링크: 상대가 링크로 들어와 자기 정보를 넣으면 상대도 무료 프로필 카드를 받는다.
4.13 무료 신살 페이지(`/free/[sal]`): 신살별 조회 + 해설 + 관련 300원 질문 연결. 로그인 없이 쓴다.
4.14 약관·환불정책·개인정보처리방침 페이지.

## 5. 질문 데이터 확장

5.1 질문과 카테고리는 `data/questions.json`에서만 읽는다. 코드에 질문 문구를 쓰지 않는다.
5.2 WHEN questions.json에 질문을 추가하면 THEN 코드 수정 없이 목록·소개 페이지·장바구니에 나타나야 한다.
5.3 WHEN 새 카테고리 코드가 추가되면 THEN 코드 수정 없이 카테고리가 나타나야 한다. (카테고리 이름·설명·이미지는 별도 데이터 파일에서 관리)
5.4 `status` 값으로 공개 여부를 정한다. 개발 중에는 `draft`도 보이게, 정식 오픈 시에는 `published`만 보이게 설정으로 바꿀 수 있어야 한다.
5.5 레시피가 없는 질문은 카테고리 공통 레시피로 동작해야 한다.
5.6 질문 데이터가 잘못되면(ID 중복, 필수 칸 누락) 빌드할 때 오류로 알려줘야 한다.

## 6. 장바구니·결제 (포트원)

6.1 결제는 장바구니 단위 건별 즉시결제다. 충전식 포인트는 만들지 않는다.
6.2 가격은 1인 질문 300원, 2인 궁합 500원(questions.json의 price 사용). 카테고리 묶음가는 설정값(`data/pricing.json`)으로 두고, 나중에 코드 수정 없이 바꿀 수 있어야 한다.
  - 1인 카테고리(30문항): 정가 9,000원 → 묶음가 7,900원 (약 12% 할인)
  - 궁합 카테고리(30문항 × 500원): 정가 15,000원 → 묶음가 12,900원 (약 14% 할인, 끝자리 900원에 맞춰 같은 수준으로 계산)
  - 질문이 늘거나 줄면 정가는 실제 질문 가격 합계로 자동 계산된다. WHEN 묶음가가 정가 이상이 되면 THEN 빌드할 때 오류로 알려줘야 한다.
6.3 묶음의 "정가"는 실제 개별가 합계만 표시한다. 근거 없는 할인 표시는 하지 않는다.
6.4 WHEN 결제 버튼을 누르기 전 THEN "결과 생성이 시작되면 환불이 제한됩니다" 고지와 동의 체크가 있어야 하며, 체크하지 않으면 결제 버튼이 눌리지 않아야 한다.
6.5 결제 전에 성인 여부(만 19세 이상)를 확인해야 한다. 만 14세 미만은 가입할 수 없다.
6.6 결제 결과는 서버에서 포트원에 다시 조회해 금액이 맞는지 검증한 뒤에만 답을 만든다.
6.7 WHEN 결제가 완료되면 THEN 장바구니의 모든 답을 바로 화면에 보여주고 보관함에 저장해야 한다.
6.8 WHEN 오류로 답이 만들어지지 않으면 THEN 그 질문은 전액 환불 대상으로 기록해야 한다.
6.9 처음에는 "테스트 결제 모드"로 흐름만 완성한다. 실제 돈이 오가지 않고, 주문·결과·보관함 저장까지 실제와 똑같이 진행된다.
6.10 최소 결제 금액은 설정값으로 둔다 (기본 300원, 결제사 최소 수수료가 있으면 900원으로 변경).

## 7. 회원·개인정보 (Supabase)

7.0 로그인은 이메일 링크 로그인(메일로 온 링크를 누르면 로그인)으로 시작한다. 카카오 로그인은 나중에 추가할 수 있게 만든다.
7.1 무료 프로필 카드는 가입 없이 볼 수 있다. 이때 생년월일은 서버에 저장하지 않는다.
7.2 가입 후에만 사주 정보·프로필·결과를 저장한다. 저장 전에 개인정보 수집·이용 동의를 받는다.
7.3 생년월일 등 개인정보를 URL(주소창)에 넣지 않는다. 공유 링크에는 무작위 토큰만 쓴다.
7.4 다른 사람의 결과·사주 정보는 볼 수 없어야 한다 (DB 행 단위 접근 제한).
7.5 회원 탈퇴 시 사주 정보와 결과를 삭제할 수 있어야 한다.
7.6 WHEN Supabase 키가 아직 없으면 THEN 개발용 임시 저장소로 동작해 화면 흐름을 확인할 수 있어야 한다.

## 8. 재방문·공유

8.1 시기 알림: 답에 나온 달이 오면 이메일로 알리고 그 달 질문을 추천한다 (가입·동의한 사람만).
8.2 공유 카드: 프로필 카드와 결과의 판정·근거 칩만 이미지로 만든다. 본문은 공개하지 않는다.
8.3 공유 이미지는 서버에서 만들고(next/og) 두 가지 크기를 제공한다. 이미지에 생년월일 같은 개인정보를 넣지 않는다.
  - 스토리용 1080×1920: 풀이꾼 장면 → 한지 판정 카드 → 이번 달 처방 + 해치 → “질문 하나에 300원, 결론부터”. 저장 버튼을 제공한다.
  - 링크 미리보기(OG) 1200×630: 왼쪽 판정 문장, 오른쪽 풀이꾼, 아래 도장.

## 9. 표시 문구 규칙

9.1 가짜 후기·평점·누적 이용 수·수상 이력을 표시하지 않는다.
9.2 "BEST/가장 많이 본"은 실제 판매 데이터가 쌓이기 전까지 "추천 질문"으로 표시한다.
9.3 "240문항", "300원"처럼 사실만 표시한다. (기준 문서의 "600문항"은 질문이 실제로 600개가 되면 사용)
9.4 공포·불안을 자극하는 문구를 쓰지 않는다.
9.5 다른 사이트의 문구·이미지·디자인을 복제하지 않는다.
9.6 ‘돈’ 대신 ‘재물’을 쓴다(재물운, 일·재물·시험).
9.7 가격은 “하나에 300원”, 궁합은 “두 사람 500원”으로 표기한다.
9.8 판정 문장은 첫 줄에 결론을 쓴다(“5월과 9월이 가장 유력해요.”). “운명이 당신을 기다립니다”, “지금 확인하지 않으면 후회해요”, “반드시 이별수” 같은 겁주는 말은 쓰지 않는다.
9.9 바닥글과 결과 화면 끝에 “풀이는 참고용 해석이며 의료·법률·투자 판단을 대신하지 않습니다.”를 표시한다.

## 10. 보안·운영

10.1 비밀값은 `.env.local`에만 두고, `.env.example`에는 이름만 적는다. GitHub에 비밀값이 올라가면 안 된다.
10.2 결제 검증과 AI 호출은 서버 코드에서만 한다.
10.3 질문당 AI 비용, 프로필 생성률, 결제 전환율, 장바구니 문항 수, 만족도, 재구매율, 초대 수락률, 환불률을 나중에 볼 수 있도록 기록한다.
10.4 GitHub `main`에 올리면 Vercel이 자동 배포한다.
